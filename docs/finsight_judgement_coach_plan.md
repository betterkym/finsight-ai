# FinSight 판단 코치 기획/아키텍처 기준안

작성 목적: 화면부터 고치는 것을 멈추고, 서비스 논리와 데이터 구조를 먼저 고정하기 위한 작업 기준 문서.

이 문서는 최종 브랜딩 문구가 아니라, 앞으로 코드와 UI를 정리할 때 따라야 할 기준선이다.

---

## 1. 지금 문제

현재 FinSight는 두 방향이 섞여 있다.

1. 기존 방향: 증권사 리포트 신뢰도 검증
2. 새 방향: 개인투자자의 매수·보유·매도 판단을 데이터로 정정해주는 판단 코치

이 둘을 그냥 한 화면에 얹으면 서비스가 난잡해진다.

사용자는 리포트 자체를 읽고 싶은 것이 아니라, 자기 판단이 흔들리는 순간에 다음 질문을 한다.

> 지금 내가 보는 근거가 이 판단에 맞는 근거인가?

그래서 리포트 검증은 버리는 것이 아니라, 전체 판단 코치 안의 한 데이터 모듈로 내려와야 한다.

---

## 2. 서비스의 임시 정의

### 한 줄 정의

FinSight는 한국 주식 개인투자자가 매수·보유·매도·추가매수를 고민할 때, 가격·거래량·수급·공시·뉴스·리포트의 시간축을 맞춰 지금 판단에서 무엇을 잘못 읽고 있는지 정정해주는 판단 코치다.

### 중요한 포인트

- 핵심은 "종목 추천"이 아니다.
- 핵심은 "리딩방처럼 매수/매도 결론을 찍는 것"도 아니다.
- 핵심은 "사용자가 붙잡은 근거가 현재 판단에 맞는지 정정하는 것"이다.
- 리포트는 메인이 아니라 사용자가 자주 붙잡는 근거 중 하나다.

### 피해야 할 표현

- "지금 사세요"
- "내일 시초에 파세요"
- "저라면 매수합니다"
- "이 종목은 오릅니다"
- "정답은 매도입니다"

### 써야 할 표현

- "이 판단에서 먼저 봐야 할 근거는 가격·거래량입니다."
- "이 리포트는 단기 매도 여부의 주된 근거로 쓰기에는 시간축이 맞지 않습니다."
- "현재 데이터만으로는 원인을 단정할 수 없고, 가능성이 높은 패턴은 A입니다."
- "이 상황에서 합리적인 판단 순서는 다음과 같습니다."

## 3. 사용 장면

FinSight는 크게 두 상황을 받아야 한다.

### A. 지금 판단 중

예시:

- "보유 중인데 내일 팔지 더 볼지 모르겠다."
- "시간외에서 올라서 지금 들어갈지 고민된다."
- "리포트 목표가가 높은데 더 들고 가도 되는지 모르겠다."

이 경우 출력은 "현재 판단 체크"가 되어야 한다.

### B. 이미 한 판단 점검

예시:

- "내가 샀더니 떨어졌다."
- "팔고 나서 올랐다."
- "뉴스 보고 들어갔는데 바로 밀렸다."

이 경우 출력은 "판단 시점 진단"이 되어야 한다.

중요: 서비스명을 "거래 복기"로 좁히면 안 된다. 이미 한 거래도 다루지만, 본질은 판단 정정이다.

## 4. 입력 구조

### 필수 입력

| 입력 | 이유 |
| --- | --- |
| 종목 | 모든 데이터 수집의 기준 |
| 현재 상태 | 신규 검토, 보유 중, 매도 완료, 추가매수 고민 등 |
| 평단 또는 매수가 | 사용자 압박과 손익 기준 |
| 투자기간 | 리포트/뉴스/수급 중 무엇을 우선할지 결정 |
| 현재 고민 | 매수, 보유, 일부매도, 전량정리, 추가매수 등 |

### 있으면 좋은 입력

| 입력 | 이유 |
| --- | --- |
| 체결 시각 | KIS 분봉·호가 연결 시 핵심 |
| 수량/비중 | 리스크 압박 판단 |
| 미수/신용 여부 | 시간 압박 판단 |
| 당시 봤던 근거 | 뉴스, 공시, 리포트, 수급, 시간외, 차트 등 |
| 매도 시각/매도가 | 이미 한 판단 점검에서 필요 |

### 리포트 입력

리포트는 필수 입력이 아니다.

리포트는 다음 조건에서만 켜진다.

- 사용자가 리포트를 참고했다고 선택
- PDF를 업로드
- 매수/보유 근거가 목표가, 투자의견, 증권사 의견인 경우

## 5. 데이터 레이어

### 5.1 KIS

역할: 체결 시점 정밀 재구성

필요 데이터:

- 체결내역
- 당일 분봉
- 현재가
- 호가
- 시간외 현재가/거래량
- 일별 기간 손익

쓰임:

- 단타/시간외 판단
- "내가 고점에서 샀는지" 판단
- "시간외 상승이 착시였는지" 판단
- "팔려면 어느 구간이 더 나았는지" 판단

주의:

- MVP에서는 read-only만 쓴다.
- 주문 API는 쓰지 않는다.
- KIS가 없으면 단기 진단 확신도는 자동으로 낮춘다.

### 5.2 KRX/pykrx

역할: 일자 기준 시장·수급 확인

필요 데이터:

- 일별 OHLCV
- 투자자별 거래대금
- 외국인·기관·개인 순매수
- 업종/시장 지수

쓰임:

- 매수 이후 외국인·기관이 따라왔는지
- 개인만 따라 산 구간인지
- 발행일/매수일 이후 가격 흐름
- 수급 이탈 여부

한계:

- 일자 단위라 체결 직전·직후 판단에는 부족하다.
- 단기/분봉 판단은 KIS가 필요하다.

### 5.3 DART

역할: 공시·실적 근거 검증

필요 데이터:

- 최근 공시
- 실적 발표
- 지분 변동
- 증자/전환사채/수주/계약/투자 공시

쓰임:

- 뉴스가 원래 공시에서 나온 내용인지 확인
- 실적 발표 후 "재료 소멸" 가능성 확인
- 공시가 매수 전 정보인지 매수 후 정보인지 확인
- 리포트의 실적 전제가 최신 공시와 맞는지 확인

한계:

- 차트 단타에는 항상 필요하지 않다.
- 공시/실적/리포트 근거가 있을 때만 핵심으로 올라온다.

### 5.4 뉴스

역할: 재료의 최초 공개 시점과 가격 반응 확인

필요 데이터:

- 기사 제목
- 보도 시각
- 원문 링크
- 같은 내용의 이전 기사/공시 존재 여부

쓰임:

- 뉴스 보고 들어간 거래가 선반영 추격인지 확인
- "호재인데 왜 내려갔는지" 설명
- 공시가 먼저였는지 뉴스가 먼저였는지 확인

한계:

- 단순 최근 뉴스 목록만으로는 부족하다.
- 반드시 체결 전후 시간순 매칭이 필요하다.

### 5.5 증권사 리포트

역할: 사용자가 붙잡은 근거가 지금 판단에 맞는지 판정

필요 데이터:

- 발행일
- 목표가
- 투자의견
- 핵심 투자 포인트
- 실적 가정
- 이후 가격/수급/공시 변화

쓰임:

- 단기 판단에 리포트 목표가를 쓰고 있는지 경고
- 손실 중 오래된 리포트를 회복 근거로 쓰는지 확인
- 목표가가 이미 가격에 반영됐는지 확인
- 리포트 전제가 최신 공시/실적과 충돌하는지 확인

중요:

기존 "리포트 신뢰도 검사"는 새 서비스 안에서 "리포트 근거 적합도 모듈"로 재정의한다.

## 6. 판단 로직 트리

### 6.1 1단계: 시간축 판정

투자기간에 따라 데이터 우선순위가 달라진다.

| 투자기간 | 1순위 | 2순위 | 리포트 비중 |
| --- | --- | --- | --- |
| 당일/내일 | 체결 시각 가격·거래량·호가 | 수급/섹터 | 낮음 |
| 1주 이내 | 가격·거래량·수급 | 뉴스/공시 | 낮음~중간 |
| 1개월 이내 | 수급·실적·공시 | 리포트 | 중간 |
| 중장기 | 실적·공시·리포트 | 가격 흐름 | 높음 |

### 6.2 2단계: 근거 종류 판정

사용자가 어떤 근거를 붙잡았는지에 따라 필요한 데이터가 달라진다.

| 사용 근거 | 반드시 필요한 데이터 | 없으면 |
| --- | --- | --- |
| 시간외 상승 | KIS 시간외 거래량/호가, 다음 정규장 초반 분봉 | 확신도 낮음 |
| 뉴스 | 뉴스 최초 시각, 전일/당일 주가 반응, 공시 선행 여부 | 선반영 단정 금지 |
| 공시/실적 | DART 원문, 공시 시각, 발표 전후 가격 | 재료소멸 단정 금지 |
| 수급 | KRX/KIS 투자자별 흐름 | 수급 이탈 단정 금지 |
| 리포트 | 발행일, 목표가, 본문, 이후 데이터 | 리포트 오용 단정 금지 |
| 차트 | 분봉/일봉 가격·거래량 | 패턴명만 낮은 확신도로 표시 |

### 6.3 3단계: 원인 후보 라벨

원인 라벨은 하나의 정답이 아니라 후보로 낸다.

예시 라벨:

- 호재 선반영 추격형
- 시간외 착시형
- 고점권 추격형
- 수급 이탈 무시형
- 낙폭과대 오판형
- 리포트 시간축 오용형
- 공포 매도 후 반등형
- 근거 공백형

각 라벨은 반드시 아래를 가진다.

- 판단 점수
- 근거
- 반대 근거
- 부족한 데이터
- 다음번 규칙

## 7. 데이터 완성도와 확신도

진단은 항상 데이터 완성도와 함께 나와야 한다.

### 데이터 완성도 점수

예시 항목:

- 가격 데이터 있음
- 거래량 데이터 있음
- 체결 시각 있음
- KRX 수급 있음
- DART 공시 있음
- 뉴스 시각 매칭 있음
- KIS 분봉 있음

### 확신도 제한 규칙

| 상황 | 제한 |
| --- | --- |
| 단기 판단인데 KIS 분봉 없음 | 확신도 최대 중간 |
| 시간외 판단인데 시간외 거래량 없음 | 확신도 최대 중간 |
| 뉴스 근거인데 최초 보도 시각 없음 | 선반영 단정 금지 |
| 공시 근거인데 DART 원문 없음 | 공시 해석 보류 |
| 리포트 근거인데 PDF/발행일 없음 | 리포트 적합도 계산 제한 |

## 8. 결과지 구조

### 기본 출력

1. 이번 판단 한 줄 진단
2. 데이터 완성도
3. 판단에 실제 사용한 데이터
4. 유리했던 신호
5. 불리했던 신호
6. 부족한 데이터
7. 정석 판단 플로우
8. 내가 놓친 체크포인트
9. 다음번 대응 규칙
10. 데이터 사용 감사표

### 리포트가 포함된 경우 추가 출력

- 이 리포트가 지금 판단에 맞는 근거인지
- 리포트 시간축과 사용자 투자기간이 맞는지
- 목표가가 이미 반영됐는지
- 리포트 전제가 최신 공시/실적과 맞는지
- 리포트를 메인 근거로 써도 되는지, 보조 근거로만 둬야 하는지

## 9. 리포트 신뢰도 검사의 새 위치

기존 기능명:

- 리포트 신뢰도 검증
- 목표가 편차
- 발행 이후 괴리
- 필요 실적
- 본문 의견 검증

새 서비스 안의 위치:

- 리포트 근거 적합도 모듈

질문을 바꾼다.

기존 질문:

> 이 리포트는 믿을 만한가?

새 질문:

> 이 리포트를 지금 내 판단 근거로 써도 되는가?

예시:

- 사용자가 내일 팔지 말지 고민 중이면 리포트 비중은 낮다.
- 사용자가 1~3개월 보유 여부를 고민 중이면 리포트 비중은 올라간다.
- 사용자가 손실 중 오래된 리포트를 들고 버티는 중이면 리포트 발행 이후 괴리가 핵심이다.

## 10. 구현 구조

현재 문제:

- `app_finsight.py`에 화면, 데이터 수집, 진단 로직이 너무 많이 섞였다.

정리 방향:

```text
report_validator/
├── app_finsight.py                 # 화면 조립만 담당
├── trade_diagnosis.py              # 판단 진단 로직
├── trade_data_pipeline.py          # KIS/KRX/DART/뉴스 데이터 수집과 특징값 생성
├── report_evidence_adapter.py      # 기존 리포트 검증 결과를 새 판단 코치에 연결
├── diagnosis_templates.py          # 결과 문장/정석 판단 플로우 템플릿
├── scoring_module.py               # 기존 리포트 점수 유지
├── timeline_module.py              # 기존 발행 이후 괴리 유지
└── retail_report.py                # 출력 리포트 생성
```

앱 파일은 최종적으로 다음만 해야 한다.

- 입력 받기
- 진단 엔진 호출
- 결과 렌더링

## 11. 2일 완성 기준

### 1일차

- 기획/아키텍처 기준 확정
- `app_finsight.py`에 임시로 넣은 진단 로직 분리
- 기존 리포트 검증을 리포트 근거 적합도 모듈로 연결
- 데이터 완성도/감사표 유지
- 화면은 버튼 2개 구조 유지

### 2일차

- KIS read-only 키 연결 구조 추가
- 체결/분봉/시간외 데이터가 없을 때와 있을 때 결과 차이 반영

## 12. 당장 코드 정리 순서

1. 현재 `app_finsight.py`에 임시로 들어간 진단 로직을 별도 모듈로 이동한다.
2. 리포트 검증 버튼은 유지하되, 새 진단 흐름에서는 "리포트 근거 적합도"로만 호출되게 한다.
3. KIS 미연동 상태에서는 단기 진단 결과에 확신도 제한을 명확히 표시한다.
4. 화면 문구는 마지막에 정리한다.

## 13. 의사결정 원칙

- UI보다 데이터 계약을 먼저 고친다.
- 데이터가 없으면 말하지 않는다.
- 원인을 하나로 단정하지 않는다.
- 리포트는 버리지 않되, 메인 엔진으로 두지 않는다.
- 사용자가 얻어야 하는 것은 "정답"이 아니라 다음 판단에서 덜 당할 기준이다.
